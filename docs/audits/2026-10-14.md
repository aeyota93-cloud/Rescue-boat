## Ошибки по приоритету

### 1. Высокий: отказ применить настройки не останавливает запуск

Место: `lib/features/connection/data/connection_repository.dart:117`.

`applyConfigOption` ожидает `changeOptions(...).run()`, но не проверяет возвращённый `Either`. Если ядро вернуло отказ, метод всё равно возвращает успех, а `connect` продолжает запуск. Снимок настроек также обновляется до подтверждения ядром.

Воспроизведение: подставное ядро возвращало `Left("synthetic rejection")`; настоящий `ConnectionRepositoryImpl.connect` вернул `Right`, а метод запуска был вызван один раз.

Последствие: новые настройки режима, маршрутов или автопереключения могут не примениться, хотя операция в приложении считается успешной.

Исправление: передавать отказ выше по цепочке и останавливать запуск/перезапуск; обновлять снимок только после успешного применения. Добавить два теста настоящего репозитория: успешное применение и отказ, запрещающий запуск.

### 2. Средний: ожидание подключения заканчивается до самого подключения

Место: `lib/features/connection/notifier/connection_notifier.dart:160–172`.

`_connect` вызывает `_singleStart.run(...)`, но не ожидает и не возвращает его Future. Поэтому вызовы `await _connect()` и `await toggleConnection()` не ожидают завершения работы репозитория. Сам `SingleCall` защищает повторный старт, но не весь набор операций остановки и перезапуска. Его параметр `onIgnored` возвращается как значение, а переданная функция уведомления не вызывается.

Воспроизведение: настоящий `ConnectionNotifier` работал с репозиторием, чей `connect` ждал управляемого Completer. `toggleConnection` уже завершился, хотя Completer ещё не был освобождён.

Последствие: вызывающий код получает ложное завершение операции; это осложняет переключение и удаление подписки и обработку ошибок. Само зависание действующего VPN этим тестом не доказывалось.

Исправление: вернуть/ожидать Future, сделать явный callback для пропущенного вызова, последовательно выполнять старт, остановку и перезапуск. Проверить медленное подключение, повторное нажатие, переключение подписки и ошибку остановки.

### 3. Средний: ошибки файла правил скрываются, а повреждение может сбросить действующие правила

Места: `lib/features/split_tunnel/notifier/split_tunnel_notifier.dart:29–42` и `:153–166`.

Файл состояния записывается непосредственно поверх старого, без временного файла. При ошибке сохранения UI уже обновлён, исключение только записывается в журнал. Наборы правил тоже пишутся с обработкой ошибок только через журнал. При повреждённом `split-tunnel.json` загрузка создаёт пустое состояние и сразу переписывает экспортированные правила этим пустым состоянием.

Два воспроизведения:

- Повреждённый файл состояния плюс существующее правило `example.org` в `via-vpn.json`: после загрузки правило исчезло из экспортированного набора.
- Вместо файла состояния создана папка с тем же именем: добавление правила нормально завершилось и обновило UI, хотя сохранить состояние было невозможно.

Последствие: пользователь считает правило сохранённым; после перезапуска оно исчезает. При повреждении файла могут потеряться маршруты, которыми пользователь управлял явно.

Исправление: атомарное сохранение с резервной копией; явная ошибка пользователю при невозможности сохранить или применить; согласованное состояние UI и файлов. При повреждении не затирать последний рабочий экспорт автоматически. Обязательны тесты отказа записи и восстановления.

### 4. Средний: параллельные соединения теряются в «Сейчас в сети»

Место: `lib/features/split_tunnel/notifier/live_connections_notifier.dart:31`.

Внутренний ключ — программа, сайт/IP и порт. Идентификатор соединения, протокол и IP при известном сайте не учитываются. Два TCP-соединения одной программы к одному сайту на порту 443 перезаписывают друг друга ещё до построения строк интерфейса.

Воспроизведение: локальный API вернул два соединения с разными ID и IP, с объёмами 11 и 22 байта. Настоящий провайдер вернул одно соединение с 22 байтами вместо двух с общими 33 байтами.

Последствие: неверные счётчик соединений, объём трафика и перечень адресов. Фактическая маршрутизация этим UI-провайдером не меняется.

Исправление: хранить соединения по ID ядра, а объединять для отображения отдельно, с суммированием чисел. Добавить проверку живого опроса API, а не только готовых списков.

Тесты интерфейса используют `FakeConnection`, подставные подписки и готовые соединения. Это правильно для проверки экрана, но такие проверки не подтверждают, что настоящее ядро запускается, останавливается, принимает настройки и сохраняет выбор. Например, тест кнопки удаления подписки подтверждает вызов подставного метода, а не реальное удаление с остановкой и последующим подключением.

В папке `test/features/rescue_ui` **65 тестов**, включая проверки точных цветов, радиусов, шрифтов, количества внутренних виджетов и витрины компонентов. Суммарное время отдельных тестов нельзя складывать как время всего запуска: файлы исполняются параллельно.

**Что стоит сохранить:**

- Приоритеты правил, разбор доменов/IP, совместимость старых файлов и миграции БД.
- Неверные ответы подписки, неверные диапазоны портов, обработку неполных строк журналов.
- Расчёт качества связи и результатов сравнения дорог.
- Действия пользователя: выбор сервера, изменение правила, копирование IP, кнопка подключения.
- Отрисовку ключевых экранов при узком окне и максимальном масштабе, отсутствие переполнений.
- Управление с клавиатуры и подписи для средств доступности.

**Что можно сократить или вынести в отдельную проверку оформления:**

- Повторяющиеся проверки одинаковых подписей и компонентов на нескольких уровнях.
- Проверки точных декоративных значений вроде радиуса 28/32 и конкретной толщины/цвета там, где это не влияет на читаемость или взаимодействие.
- Проверки количества внутренних `Container`, `Text`, `FrameTag`: они привязывают тест к реализации.
- Три полные отрисовки демонстрационной витрины при каждой мелкой правке логики; их можно запускать отдельно при изменениях UI-кита.

Убирать все проверки оформления или задавать цель «сократить число тестов вдвое» не стоит. Сначала отделить проверку поведения от проверки дизайна, затем объединять дубли. Общий высокий процент покрытия также не нужен: важнее закрыть реальные отказы и жизненный цикл подключения.

Дополнительно: `flutter_test` в `pubspec.yaml` закомментирован. Сейчас пакет доступен, но тесты должны объявлять SDK-зависимость явно, чтобы не зависеть от косвенного состава пакетов. Это также устранит соответствующие замечания анализатора.

## Качество кода

Хорошая основа: модели и преобразования правил отделены от виджетов; многие операции являются чистыми функциями; в сравнении путей подменяются часы и интервалы; чтение статистики использует кэш и отдельный изолят для больших данных. Переписывать приложение целиком не нужно.

Слабые места:

1. Асинхронные ошибки иногда подавляются или превращаются в успех. Это важнее косметического форматирования.
2. Работа с сохранением правил синхронна и содержит скрытые отказы. Перенос записи в фон сам по себе не решит проблему согласованности.
3. Состояние подключения управляется несколькими независимыми слушателями и методами, без общей последовательности операций.
4. Крупные экраны: серверы — 1212 строк, ошибки — 887, сравнение путей — 763. Разделять лучше по обязанностям: операции с подписками/выбором сервера, диалоги и части экрана. Просто переносить каждую маленькую функцию в свой файл не требуется.
5. Сохранились неиспользуемые импорты, старый `restartInPlace` без вызывающего кода и прежние вспомогательные решения выбора серверов. Чистить постепенно, начиная с изменяемых файлов; не смешивать широкую уборку Hiddify с исправлениями подключения.

Остальное время — получение исходников, упаковочные инструменты, загрузка файлов и публикация. Значения всего запуска получены по `run_started_at` и `updated_at`, поэтому включают служебное завершение workflow.

Источник для стабильной версии: [GitHub Actions: сборка 0.2.1](https://github.com/aeyota93-cloud/Rescue-boat/actions/runs/38522026871)

**Тесты не являются причиной задержки:** в текущем workflow нет ни `flutter test`, ни `dart analyze`.

Установщик и портативная версия собираются двумя вызовами Fastforge. Это не просто два одинаковых архива: portable получает `--build-dart-define=portable=true`; от этого зависят папка данных и настройки (`Environment.isPortable`). Поэтому объединить обе упаковки вокруг одного текущего бинарника без изменения этой логики нельзя. `--skip-clean` пропускает очистку, а не компиляцию: [документация Fastforge](https://fastforge.dev/cli)

SDK и pub-зависимости уже кэшируются через `subosito/flutter-action@v2.21.0` с `cache: true`. Совет «просто включить кэш Flutter» здесь ничего не изменит. Action предоставляет признаки попадания в SDK/pub-кэш; стоит сначала вывести их в журнал: [документация flutter-action 2.21.0](https://github.com/subosito/flutter-action/tree/v2.21.0#caching)

Дополнительные потери времени:

- Один коммит `75a8aaa7` вызвал сборки и для `main`, и для тега `v0.2.1`. Группа concurrency содержит полный ref, поэтому эти сборки не объединяются.
- Изменение только `appcast.xml` тоже запускает полноценную сборку: файл не исключён через `paths-ignore`. Запуск для `b848cc9a` успешно собирал приложение повторно после изменения лишь даты в ленте обновлений; код приложения не менялся.
- test2 и стабильная версия собирались последовательно, хотя код приложения был одинаковым. Сам процесс выпуска поэтому дольше одной сборки.
- `dart pub global activate fastforge` не закрепляет версию упаковщика. Это риск воспроизводимости, хотя в измеренных запусках шаг занимал только 1–8 секунд и ускорять его первым бессмысленно.
- Переводы генерируются через `slang_build_runner` и дополнительно `dart run slang`. Стоит проверить необходимость второго полного прохода, а не удалять его без сравнения результатов.

**Порядок оптимизации:**

1. Разделить быструю проверку кода и сборку релиза. В проверку включить тесты и подготовленный анализатор; релиз пропускать только после успеха проверки.
2. Убрать повторную полную сборку при обновлении `appcast.xml`; избежать двух компиляционных запусков одного релизного коммита для ветки и тега.
3. При неизменных исходниках, версии ядра, версии приложения и параметрах использовать уже проверенные файлы тестового выпуска для стабильной публикации. Проверять происхождение файлов и контрольные суммы. Изменившийся код требует новой сборки.
4. Закрепить версию Fastforge; разделить подготовку и упаковку на измеряемые шаги; проверить попадания в существующий SDK/pub-кэш и необходимость повторной генерации переводов.
5. При необходимости отдельно кэшировать архив ядра по `dependencies.properties` и результаты генерации вместе с корректными ключами. Кэширование поддерживается GitHub Actions для зависимостей и промежуточных результатов: [документация GitHub Actions](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching) . Полный кэш Windows/CMake и `.dart_tool` требует особой осторожности с путями и версиями инструментов и не должен быть первым шагом.
6. Для дальнейшего сокращения двух компиляций можно перевести выбор portable-папки в поведение при запуске и упаковывать один бинарник двумя способами. Это изменение поведения хранения данных, его нужно проверять отдельно; это не безопасная однострочная оптимизация.

Прогноз нового времени без проверочной сборки был бы догадкой. Наиболее надёжный первый выигрыш — убрать лишние запуски и повторное ожидание уже проверенных файлов. Ни сокращение 371 теста, ни замена всех маленьких проверок одним тестом длительность текущей релизной сборки не уменьшит.
